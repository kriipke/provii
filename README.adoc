= provii
:doctype: article
:description: A lightweight installer for precompiled command-line tools
:toc:
:toclevels: 2
:imagesdir: share

image::provii.png[provii,width=200]

`provii` downloads precompiled command-line tools and installs their executables,
man pages, and shell completions when available. It is for developers who move
between workstations, VMs, and containers and want tools such as `fd`, `rg`, `jq`,
and `fzf` without building them from source.

The project consists of a shell entrypoint and Bash installer recipes in
link:repository/[repository/]. Recipes select upstream release assets for the
current operating system, architecture, and Linux libc. Installations can use
user-owned directories or system locations.

== Status and compatibility

The current development script identifies itself as *0.4.3*. Historical RPM/DEB
releases include *0.3.1*; those packages predate the latest compatibility work.
See https://github.com/kriipke/provii/releases[GitHub releases] for published
artifacts and https://github.com/kriipke/provii/tags[tags] for source versions.
This README describes the current `main` branch.

The link:.github/workflows/ci.yml[CI workflow] checks syntax and the installer
manifest, and smoke-tests these combinations:

[cols="1,1,2",options="header"]
|===
|Operating system |Architecture |Tools covered by installation smoke tests
|Ubuntu Linux |x86_64 |jq, fd, rg, glow
|Ubuntu Linux |ARM64 |jq, fd, rg, glow
|macOS |Apple Silicon |jq, fd, rg, glow
|macOS |Intel |jq, rg, glow
|===

Support varies by recipe and upstream release assets. This matrix does not
promise that every recipe works on every platform. Other Linux distributions
and libc variants need broader verification.

Use *Bash* to invoke the entrypoint; installer recipes also run in Bash.
The script retains a `/bin/sh` shebang and CI exercises `sh` on its runners,
but strict POSIX shell portability is not established. Invoke `bash provii`
explicitly on systems whose `sh` differs from those runners.

== Requirements

* Bash, `curl`, and standard Unix utilities including `awk`, `sed`, `grep`, and `install`.
* `jq` for GitHub API responses. The script attempts to download it when absent;
  installing it with your system package manager first is recommended.
* Archive tools required by the chosen recipe: `tar`, `unzip`, and/or xz support.
* On Linux, `ldd` for libc detection.
* Network access to GitHub and upstream download hosts.
* Git for the checkout-based quickstart below.

Man pages and shell completions depend on the selected recipe and local setup.
A `GITHUB_TOKEN` environment variable is optional for authenticated GitHub API
requests; keep it outside the repository.

== Quickstart from a checkout

[source,bash]
----
git clone https://github.com/kriipke/provii.git
cd provii
bash ./provii ls
bash ./provii cat fd
----

`ls` lists compatible recipes. `cat` prints a recipe for inspection without
running that recipe. Startup may still perform a network version check or
bootstrap `jq` if missing.

For a user-scoped installation, first choose directories explicitly:

[source,bash]
----
mkdir -p "$HOME/.local/bin"
export PATH="$HOME/.local/bin:$PATH"
export PROVII_SCOPE=user
export PROVII_USER_BIN="$HOME/.local/bin"
export PROVII_USER_MAN="$HOME/.local/share/man"
export PROVII_USER_BASH_COMP="$HOME/.local/share/bash-completion/completions"
export PROVII_USER_ZSH_COMP="$HOME/.local/share/zsh/site-functions"

bash ./provii env fd
bash ./provii install fd
"$HOME/.local/bin/fd" --version
----

The completion directories must be part of your shell's completion search path
to take effect. Run these commands from the repository root to use its local
recipes; outside that directory, provii fetches recipes from GitHub.

== Install the entrypoint on your PATH

You can keep the entrypoint without a full checkout:

[source,bash]
----
mkdir -p "$HOME/.local/bin"
curl -fSL https://raw.githubusercontent.com/kriipke/provii/main/provii -o "$HOME/.local/bin/provii"
chmod 755 "$HOME/.local/bin/provii"
export PATH="$HOME/.local/bin:$PATH"
bash "$HOME/.local/bin/provii" ls
bash "$HOME/.local/bin/provii" install fd
----

Use `bash "$HOME/.local/bin/provii" ...` explicitly for the shell compatibility
reason described above. The URL tracks `main`; replace `main` with a tag or
commit when you need a fixed entrypoint version. Recipes default to `main`
independently of the entrypoint version.

The historical CDN is not required for these instructions. Historical RPM and
DEB packages remain on the releases page, but the packaging workflow and package
metadata need updating before a new package release is advertised here.

== Commands

[source,bash]
----
bash ./provii                       # usage
bash ./provii ls                    # list compatible recipes
bash ./provii cat fd                # inspect a recipe
bash ./provii env fd                # inspect resolved installation settings
bash ./provii install -i fd         # request confirmation before installation
bash ./provii install fd rg         # install multiple tools
bash ./provii install -b main fd    # choose the remote recipe branch
----

The `-b` option affects remote recipe retrieval. A matching recipe in the local
`repository/` directory takes precedence. `env` gathers facts and can create
configuration/cache directories; it is not a filesystem dry run.

The historical link:provii.1[man page] documents additional commands and options.
Some examples in it predate the current implementation.

== Configuration

provii sources a shell configuration file at `${XDG_CONFIG_HOME:-$HOME/.config}/proviirc`.
See link:proviirc[proviirc] for an example. It is shell code, so use a file you
control. Values in the configuration can override exported environment settings.

[source,bash]
----
mkdir -p "$HOME/.config"
cp proviirc "$HOME/.config/proviirc"
# Edit the copied file for your installation paths.
----

[cols="1,3",options="header"]
|===
|Variable |Purpose
|`PROVII_SCOPE` |`user` or `system`; defaults according to whether the process runs as root.
|`PROVII_USER_BIN`, `PROVII_SYSTEM_BIN` |Executable destination for the chosen scope.
|`PROVII_USER_MAN`, `PROVII_SYSTEM_MAN` |Man-page destination.
|`PROVII_USER_BASH_COMP`, `PROVII_SYSTEM_BASH_COMP` |Bash completion destination.
|`PROVII_USER_ZSH_COMP`, `PROVII_SYSTEM_ZSH_COMP` |Zsh completion destination.
|`PROVII_CACHE` |Temporary installation directory; defaults under `${XDG_CACHE_HOME:-$HOME/.cache}/provii`.
|`PROVII_LOG` |Installation log location.
|`PROVII_OS`, `PROVII_ARCH`, `PROVII_LIBC` |Override detected platform details; normally leave unset.
|`GITHUB_TOKEN` |Optional GitHub API token, supplied through the environment.
|===

Use `env` to inspect resolved paths rather than assuming that every machine
uses the same defaults. Prefer explicit user destinations when trying a recipe.

== How installation works

. Gather platform facts and resolve installation destinations.
. Read a local recipe or fetch one from GitHub.
. Show the installation targets and run the recipe in a Bash subprocess.
. Download upstream assets and install the requested files.

Recipes are executable shell code. Download checksum verification and
transactional rollback are not implemented consistently; inspect recipes and
use trusted upstream sources. Tools installed by provii retain their own licenses.

== Development and verification

[source,bash]
----
# Run from the repository root; these checks do not install tools.
bash -n provii
sh -n provii
for recipe in repository/*; do
  [ "${recipe##*/}" = manifest.json ] || bash -n "$recipe"
done
make manifest
git diff --exit-code repository/manifest.json
----

`make manifest` requires `jq` and rewrites the manifest. The current generator
also includes `manifest.json` itself; excluding metadata is follow-up work.

The link:.github/workflows/ci.yml[CI installation smoke tests] perform actual
downloads and installations in runner temporary directories. The older Bats
suite and generator in link:tests/[tests/] contain stale paths and are not
currently a reliable one-command test suite.

== Remaining work

Concrete opportunities include download integrity verification, reliable failure
recovery, repairing the offline regression suite, refreshing package releases,
and expanding the tested compatibility matrix. These are candidate areas rather
than a claim that all work is scheduled. Maintainer-selected issues should state
scope and completion criteria before being used as a project commitment.
